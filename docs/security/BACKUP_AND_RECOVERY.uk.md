# Backup і відновлення — принцип роботи та безпечна процедура

**🇺🇦 Українська** · [🇬🇧 English](BACKUP_AND_RECOVERY.en.md) · [🇫🇷 Français](BACKUP_AND_RECOVERY.fr.md) · [🇩🇪 Deutsch](BACKUP_AND_RECOVERY.de.md) · [🇪🇸 Español](BACKUP_AND_RECOVERY.es.md) · [🇰🇷 한국어](BACKUP_AND_RECOVERY.ko.md) · [🇯🇵 日本語](BACKUP_AND_RECOVERY.ja.md)

> Актуально для MD Notes v0.3.23. Канонічна версія — українська. Backup/restore реалізовано з v0.3.22; автоматизовані desktop-тести є, але окремого повного ручного owner runtime-тесту процедури ще не зафіксовано.

## 1. Backup, sync і Git — це різні речі

**Backup** — самодостатній ZIP-знімок, призначений для відновлення.

**Sync** — механізм, що підтримує актуальні копії між місцями. Помилкове видалення або пошкодження може синхронізуватися теж.

**Git** — історія версій і обміну файлами. Він корисний, але не містить усіх локальних даних автоматично й не є резервною копією ключів encrypted vault.

Для важливого сховища варто мати щонайменше одну резервну копію, незалежну від робочої папки й синхронізації.

## 2. Що робить «Створити резервну копію…»

Команда в меню **Файл → Створити резервну копію…**:

1. намагається зберегти відкриті документи;
2. обходить фізичні файли поточного vault;
3. відкидає службові дані, які не повинні переноситися;
4. для кожного включеного файла рахує SHA-256;
5. записує файли у ZIP;
6. додає відкритий `manifest.json`;
7. ще раз перевіряє, що джерело не змінилося під час операції;
8. лише після успіху перейменовує тимчасовий файл у вибране ім’я backup.

Якщо vault активно змінювався під час створення копії, операція має завершитися помилкою, а не тихо створити змішаний знімок.

## 3. Що входить у backup

Зазвичай входять:
- Markdown-нотатки;
- вкладення;
- `.mdnotes/config.json`;
- schema;
- templates/views та інші переносимі службові файли;
- `.mdnotes/trash/`;
- конфігурація encrypted vault, якщо він зашифрований.

## 4. Що НЕ входить

Вбудований backup виключає:
- `.git/`;
- `.mdnotes/cache/`;
- тимчасові файли MD Notes;
- типові системні `.DS_Store`, `Thumbs.db`, `desktop.ini`;
- приватні age-ключі й recovery private key, бо вони не повинні лежати у vault.

Символічні посилання в backup не приймаються: це захист від несподіваного виходу за межі сховища.

## 5. Manifest

`manifest.json` містить:
- формат `md-notes-backup`;
- версію формату;
- версію застосунку, яка створила копію;
- час створення;
- назву vault;
- ознаку `encrypted`;
- список файлів;
- для кожного файла — відносний шлях, розмір і SHA-256.

Manifest потрібен не для шифрування, а для **перевірки повноти й цілісності**.

Він відкритий, тому backup-файл може розкривати певні метадані навіть тоді, коли самі дані encrypted vault залишаються шифротекстом.

## 6. Технічні межі формату v1

Поточна реалізація захищає restore лімітами:
- до 100 000 файлів;
- до 4 GiB для одного файла;
- до 16 GiB сумарного розміру;
- без небезпечних абсолютних шляхів, `..` та path traversal;
- без дубльованих шляхів;
- без колізій шляхів, що відрізняються лише регістром.

Це навмисні межі безпечного portable backup.

## 7. Як працює перевірка перед restore

**Файл не розпаковується в кінцевий vault одразу.**

Спочатку MD Notes:
1. читає `manifest.json`;
2. перевіряє формат і версію;
3. перевіряє всі відносні шляхи;
4. перевіряє, що у ZIP немає неочікуваних/дубльованих записів;
5. звіряє розміри;
6. перераховує SHA-256 кожного файла;
7. перевіряє, що всі файли з manifest є й зайвих немає.

Якщо хоча б одна перевірка не проходить, restore зупиняється до створення робочого vault.

## 8. Куди відновлюються дані

Після повної перевірки файли спочатку розпаковуються у тимчасову папку. Лише успішний результат перетворюється на новий vault.

MD Notes **не перезаписує існуючу папку**. Назва вибирається на кшталт:

```text
My Vault-restored
My Vault-restored-2
My Vault-restored-3
```

Це дозволяє порівняти старий і відновлений стан та зменшує ризик знищити останню робочу копію.

## 9. Звичайний vault

Для звичайного незашифрованого vault ZIP містить самі Markdown/вкладення у читабельній формі. Тому backup треба захищати так само, як оригінальну папку.

Не надсилайте backup незашифрованого vault у недовірене місце лише тому, що це «службовий ZIP».

## 10. Зашифрований vault

Для encrypted vault backup читає **фізичні файли на диску**, тому нотатки/вкладення, які лежать як age ciphertext, потрапляють у ZIP саме як ciphertext.

При цьому:
- `.mdnotes/encryption.json` і частина службових метаданих лишаються відкритими;
- `.mdnotes/cache` не входить;
- приватний ключ не входить;
- recovery private key не входить.

Отже для повного аварійного відновлення потрібні **дві незалежні речі**:
1. backup vault;
2. хоча б один приватний age-ключ, який входить до recipients цього vault.

Детально: [Зашифроване сховище](ENCRYPTED_VAULT.uk.md).

## 11. Рекомендована схема резервування

Для важливого vault:

- робоча копія на основному пристрої;
- регулярний MD Notes backup на іншому фізичному диску або в іншому сховищі;
- ще одна копія поза основним місцем, якщо дані критичні;
- для encrypted vault — recovery key окремо від усіх копій vault.

Принцип **3-2-1** добре підходить як орієнтир: кілька копій, різні носії, принаймні одна поза основним місцем.

## 12. Процедура створення backup

1. Завершіть або збережіть критичні редагування.
2. Виберіть **Файл → Створити резервну копію…**.
3. Збережіть ZIP не всередині самого vault.
4. Переконайтеся, що застосунок повідомив про успіх.
5. Не перейменовуйте внутрішні записи ZIP вручну.
6. Для важливих даних скопіюйте ZIP на незалежний носій.
7. Для encrypted vault перевірте, що recovery key зберігається окремо.

## 13. Процедура відновлення

1. Не видаляйте пошкоджений/старий vault перед перевіркою restore.
2. Виберіть **Файл → Відновити резервну копію…**.
3. Вкажіть backup ZIP і батьківську папку для нового vault.
4. Дочекайтеся успішної перевірки manifest/checksums.
5. Відкрийте створений `*-restored` vault.
6. Перевірте кілька важливих нотаток, вкладень і граф.
7. Для encrypted vault за потреби імпортуйте приватний ключ.
8. Лише після перевірки вирішуйте, що робити зі старою копією.

## 14. Recovery drill

Backup, який ніколи не пробували відновити, дає менше впевненості.

Періодично варто:
1. взяти актуальний backup;
2. відновити його в окрему папку;
3. відкрити кілька нотаток;
4. перевірити attachments/graph;
5. для encrypted vault — переконатися, що доступний recovery key;
6. видалити тестовий restored vault після перевірки, якщо він не потрібен.

Це **перевірка процедури**, а не лише наявності ZIP.

## 15. Типові помилки

- backup лежить на тому самому диску, який може фізично вийти з ладу;
- є ciphertext, але немає ключа;
- є ключ, але немає актуальної копії vault;
- користувач вважає sync повноцінним backup;
- ZIP звичайного vault завантажено у публічне місце;
- стару папку видалено до перевірки restored copy;
- backup створюється під час масового зовнішнього переписування файлів.

## 16. Що робити при помилці checksum

Не «виправляйте» manifest вручну.

Checksum mismatch означає, що архів не відповідає описаному знімку. Збережіть проблемний ZIP для аналізу, спробуйте іншу резервну копію або створіть нову з джерела, якщо воно ще доступне.

## 17. Для ШІ та автоматизації

AI не повинен:
- видаляти останню відому добру копію перед перевіреним restore;
- вважати sync/Git еквівалентом backup;
- додавати приватний ключ у ZIP;
- обходити checksum/path validation;
- розпаковувати поверх існуючого vault;
- заявляти успішне відновлення без фактичної перевірки створеного `*-restored` vault.

Правила encrypted data: [ENCRYPTED_VAULT_CONTRACT.md](../ai/ENCRYPTED_VAULT_CONTRACT.md).

## Перевірка recovery для 1.0

Перед desktop 1.0 додано автоматизований end-to-end recovery drill для encrypted vault:

1. створюється справжнє зашифроване сховище з окремим recovery recipient;
2. записується Markdown-нотатка та імпортується бінарне вкладення;
3. створюється portable ZIP backup;
4. backup відновлюється в нову папку;
5. відновлене сховище відкривається **recovery private key**;
6. тест читає відновлену нотатку й байти вкладення через encrypted storage provider.

Цей сценарій пройшов у CI перед 1.0 на Windows, macOS і Linux core gates. Це автоматизований доказ механізму recovery, але він не підміняє окремий ручний тест власника на реальних даних.
