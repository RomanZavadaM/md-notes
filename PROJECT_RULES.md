# PROJECT_RULES — постійні правила MD Notes

Цей файл є канонічним джерелом постійних правил проєкту. **Будь-яка нова сесія або новий чат починається з `START_HERE.md`**, після чого потрібно прочитати `PROJECT_RULES.md`, `PROJECT_STATE.md` і `WORKLOG.md`.

## 1. Джерела істини

- `START_HERE.md` — обов'язкова перша точка входу для нового чату, нової сесії або відновлення після обриву.
- `PROJECT_RULES.md` — постійні правила.
- `PROJECT_STATE.md` — лише інтегрований стан `main`: checkpoint, версія та наступний великий крок.
- `WORKLOG.md` — оперативний знімок активної роботи: поточний slice, гілка/PR, останній перевірений SHA, блокери й точна наступна дія.
- GitHub Issue #8 `MD Notes — live development ledger` — append-only журнал переходів стану активної роботи.
- `Cargo.toml` (`[workspace.package] version`), `app/package.json` і `app/src-tauri/tauri.conf.json` — основні машинні джерела номера версії; їх синхронізує release-please. Кореневий `version.txt` — лише похідний compatibility marker для стратегії release-please `simple`, не окреме джерело істини; CI зобов'язаний перевіряти його рівність основним джерелам і `app/package-lock.json`.
- `docs/releases/` — незмінні нотатки опублікованих релізів.
- `docs/adr/` — прийняті архітектурні рішення.
- Якщо старий чат або застарілий документ суперечить актуальному `main`, пріоритет має `main`.
- Для незлитої роботи джерелом істини є активна гілка/PR, `WORKLOG.md` у цій гілці та останні записи Issue #8, а не пам'ять чату.

## 2. Активний продукт

- Активний продукт: Tauri 2 застосунок `app/` (React + TypeScript) і ядро `crates/notes-core` (Rust).
- Цільові платформи: Windows, macOS, Android, iOS. Linux збирається як додаткова платформа.
- Дані користувача — звичайні відкриті файли (Markdown, вкладення, JSON). Застосунок не створює прихованих або закритих форматів даних. Виняток: опціональне зашифроване сховище у відкритому документованому форматі age (ADR-0007); створюється лише явною дією користувача, звичайні сховища не змінюються.

## 3. Версіювання

Поки продукт має статус 0.x:

- функціональний етап піднімає minor: `0.1.x -> 0.2.0`;
- виправлення, юридичне/пакувальне доопрацювання або сумісна корекція піднімає patch: `0.1.0 -> 0.1.1`;
- версія формується з Conventional Commits через release-please; вручну номери версій у коді не змінюються;
- уже опублікований Git tag та GitHub Release не пересуваються й не переписуються.
- `docs`, `ci` і службові `chore` зміни самі по собі не повинні створювати нову продуктову версію; release-please має формувати release PR лише коли після останнього checkpoint є релізно значущі продуктові зміни (`feat`, `fix`, `perf` або окремо погоджений release-driving commit).

Перехід до `1.0.0` робиться лише за окремим рішенням власника проєкту.

Після встановлення stable 1.x:

- сумісне виправлення піднімає patch: `1.0.0 -> 1.0.1`;
- сумісна нова функція піднімає minor: `1.0.x -> 1.1.0`;
- несумісна зміна формату/контракту потребує окремого рішення власника і major bump;
- номер версії й надалі формує release-please з Conventional Commits; вручну машинні версії не змінюються.

### Тестові збірки між релізами

- Номер продукту (`0.x.y`) і номер тестової ревізії (`rN`) — різні речі. Тестова ревізія не змінює машинну версію в `Cargo.toml`, `app/package.json` чи `tauri.conf.json`.
- Опубліковані release assets мають канонічні назви з реальною версією, наприклад `MD-Notes-0.3.22-Windows-x64-portable.zip`.
- Одноразові runtime-test artifacts повинні бути явно позначені як тестові й не маскуватися під опублікований реліз. Допустимий шаблон: `MD-Notes-TEST-<scope>-rN-<shortSHA>-<platform>.zip`.
- `rN` — послідовна тестова ревізія поточного незавершеного приймання; видану на тест ревізію не перевикористовувати для інших байтів. Наступний кандидат отримує наступний `rN`.
- SHA в назві тестового артефакту і окремий SHA256 файла потрібні для однозначного відтворення; вони не є частиною SemVer продукту.
- Після owner PASS і повного release checkpoint тестова назва не переноситься у GitHub Release: реліз знову отримує лише канонічний `vX.Y.Z` та стандартні назви assets.

## 4. Дані та приватність

- MD Notes працює local-first: нотатки, вкладення та індекс залишаються на пристрої користувача або у вибраному ним сховищі.
- Нотатки, вкладення, ключі доступу та особисті файли користувача ніколи не проходять через сервери MD Notes; таких серверів немає.
- Не додавати аналітику, телеметрію, session replay, remote fonts чи сторонні скрипти стеження.
- Паролі й токени мережевих та хмарних сховищ зберігаються лише в системному сховищі секретів ОС, ніколи у файлах сховища, `localStorage` чи Git.
- Конфлікти синхронізації ніколи не перезаписуються мовчки (див. ADR-0005).
- Застосунок не змінює файли користувача без потреби: відкриття папки не модифікує її, видалення переносить у `.mdnotes/trash/`.
- Зашифроване сховище (ADR-0007): приватні ключі age зберігаються лише в системному сховищі секретів ОС і ніколи у файлах сховища, `localStorage`, Git чи логах; відкритий текст нотаток і вкладень у зашифрованому режимі не записується на диск (шифрування в пам'яті до запису); власну криптографію не писати; кеш/індекс `.mdnotes/cache` у MVP лишається відкритим локальним кешем поза синхронізацією (ADR-0002) і не потрапляє в Git; режим вмикається лише явною дією користувача, а без нього й для звичайних сховищ поведінка не змінюється (збірка без feature `encrypted-vault` - повний продукт без шифрування).
- Будь-яку зміну цих меж довіри спершу обговорити з власником.

## 5. Якість коду

- Код, коментарі та ідентифікатори — англійською; документація — українською (з перекладами за розділом 9).
- Логіка даних живе в `notes-core` і покривається тестами; шар Tauri лише перетворює виклики інтерфейсу на виклики ядра.
- Шляхи всередині сховища завжди відносні та перевіряються на вихід за межі сховища.
- Запис файлів — атомарний.
- Користувацькі рядки не вбудовуються в бізнес-логіку; інтерфейс бере їх із мовних пакетів.

## 7. Перед merge

Для змін у коді обов'язково:

1. `cargo fmt --all --check`;
2. `cargo clippy --workspace --all-targets -- -D warnings`;
3. `cargo test -p notes-core`;
4. `npm ci` і `npm run build` у `app/` (перевірка типів TypeScript і збірка інтерфейсу);
4a. license gate: `cargo deny check licenses` і `npm run licenses` у `app/`;
5. lock-файли (`Cargo.lock`, `app/package-lock.json`) актуальні; Rust CI запускається з `--locked`/`cargo metadata --locked`, тому застарілий `Cargo.lock` є blocker; за потреби оновити lockfile контрольованим workflow/PR;
6. для user-visible змін — перевірити зміну в запущеному застосунку (`npm run tauri dev`) або чесно зазначити в PR, що runtime-перевірки не було;
7. version, показана в інтерфейсі, походить з build metadata; hardcoded номери версій в UI заборонені;
8. перевірити, що робочі сховища, особисті нотатки, ключі, БД індексу та персональні файли не потрапили до Git.

CI використовує path-aware routing і не повинен без потреби запускати дорогі jobs:

- docs-only PR (`**/*.md`, `docs/**`) не запускає heavy CI;
- draft PR не запускає heavy CI; фінальна перевірка стартує при `ready_for_review`;
- frontend-only зміни проходять Node/frontend build без Rust matrix і без Mobile smoke;
- Rust/core/Tauri зміни проходять повний Rust matrix на Linux/Windows/macOS + Tauri clippy;
- Android/iOS Mobile smoke запускається автоматично лише для ready/non-draft змін, що зачіпають native/core/dependency boundary, або вручну через `workflow_dispatch`;
- license/advisory gates запускаються при зміні dependency metadata або консервативно для невідомих non-doc paths; окремий weekly `Security audit` перевіряє RustSec та production npm advisories навіть без змін коду;
- невідомі non-doc paths за замовчуванням отримують повну перевірку, а не пропускаються;
- release-please PR не повинен запускати повний Rust/Tauri/Mobile набір; для нього достатні release metadata/version consistency **і** `cargo metadata --locked`; version bump у `Cargo.toml` змінює workspace package versions у `Cargo.lock`, тому release PR не можна зливати, доки lockfile не оновлено на ту саму версію;
- docs-only та workflow-only push у `main` не запускає release-please;
- реальний release packaging не можна ставити на `cancel-in-progress`, щоб наступний push не обірвав публікацію assets;
- `cancel-in-progress` дозволений для звичайного CI/Mobile PR feedback.

Перед merge все одно мають бути зеленими **усі релевантні checks для типу зміни**. Path routing оптимізує зайві запуски, але не скасовує обов'язкові перевірки. Зелений CI не замінює runtime-перевірку user-visible змін.

## 8. Реліз

Кожний GitHub Release повинен мати:

- унікальний tag `vX.Y.Z`;
- release notes у `docs/releases/RELEASE_NOTES_vX_Y_Z.md` і запис у `CHANGELOG.md`;
- START/source пакет;
- доступні платформні пакети для підтримуваної release-лінії: для stable desktop 1.x — Windows, macOS і Linux; Android/iOS build-smoke не вважається mobile release asset до окремого physical-device/store acceptance;
- `SHA256SUMS.txt`;
- legal notices (`LICENSE.md`, `COPYRIGHT.md`, `THIRD_PARTY_NOTICES.md`);
- чітке маркування signing-статусу та обмежень тестової збірки.

Для 0.x релізи за замовчуванням публікуються як **prerelease**, доки власник не визначить стабільну виробничу лінію.

## 10. Захист main

- Роботу вести через окрему гілку + PR.
- Merge робити після успішних checks.
- Для публічного репозиторію GitHub ruleset/branch protection має вимагати PR та успішні checks, коли адміністративні налаштування доступні.
- Відсутність технічного ruleset не скасовує ці правила розробки.

## 11. Команда власника «злити у main», інтеграція і тестові релізи

Щоб не плутати технічний merge з релізною командою власника, використовувати такі терміни:

- **«інтегрувати PR у `main`»** — звичайний технічний merge завершеного slice після зелених checks; сам по собі не означає новий GitHub Release;
- **«злити у `main`» / «зливай у `main`»** — команда власника на **повний тестовий релізний checkpoint для всіх підтримуваних систем**.

Команда **«злити у `main`»** означає повний цикл:

1. завершити поточний функціональний scope і документацію (усіма мовами за розділом 9);
2. пройти перевірки розділу 7;
3. інтегрувати PR у `main`;
4. інтегрувати release PR від release-please (версія, CHANGELOG);
5. додати release notes у `docs/releases/` і оновити PROJECT_STATE/WORKLOG;
6. виконати release builds/package для всіх підтримуваних платформ;
7. сформувати START/source, `SHA256SUMS.txt` і legal notices;
8. опублікувати незмінний Git tag та GitHub Release: для stable 1.x patch/minor — **stable** за замовчуванням; prerelease використовувати лише для явно тестового/preview checkpoint;
9. перевірити опубліковані assets і зафіксувати release SHA/run у WORKLOG та Issue #8.

Ритм:

- кожен самодостатній функціональний slice після зелених checks можна **інтегрувати PR у `main`** до початку наступного slice;
- повне **«злиття у `main`»** з релізами всіх систем — орієнтовно після **2–3 user-visible integrated slices**, раніше після ризикових змін формату даних або негайно за прямою командою власника;
- кожен такий checkpoint отримує нову версію; опубліковані tag/release не пересуваються й не переписуються.

## 12. Обов'язковий журнал активної роботи

Щоб розробка не залежала від пам'яті конкретного чату:

1. Перед початком нового slice або після відкриття нового чату прочитати `START_HERE.md`, `PROJECT_RULES.md`, `PROJECT_STATE.md`, `WORKLOG.md` і останні записи Issue #8.
2. До суттєвих змін зафіксувати в `WORKLOG.md`: мету slice, базовий `main` SHA, активну гілку, PR (якщо вже є), критерії готовності та наступну дію.
3. Після кожної зміни стану додати короткий коментар у Issue #8: створено гілку, реалізовано суттєвий блок, пройдено перевірки, відкрито PR, CI pass/fail, merge, виявлено blocker.
4. `WORKLOG.md` оновлювати при кожному змістовному checkpoint. Він має завжди дозволяти продовжити роботу без цього чату.
5. Статус `DONE` ставити тільки після merge у `main`. Зелений PR до merge — це `VERIFIED`, але ще не `DONE`.
6. Після merge оновити `WORKLOG.md`: записати merge SHA, перенести slice у «Нещодавно завершено», визначити рівно одну наступну активну дію.
7. `PROJECT_STATE.md` оновлювати лише тоді, коли зміна вже інтегрована або суттєво змінює підтверджений стан проєкту.
8. Якщо чат обірвався, не відновлювати роботу з припущень: знайти активний PR/branch, звірити SHA з `WORKLOG.md` та Issue #8 і продовжити з першої незавершеної дії.

## 13. Issues

- Не прикріплювати до відкритих issues особисті нотатки, сховища, індекси, токени або файли з персональними даними.
- Шаблони: `.github/ISSUE_TEMPLATE/bug_report.md`, `.github/ISSUE_TEMPLATE/improvement.md`.
